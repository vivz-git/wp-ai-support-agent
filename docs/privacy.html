Kettle & Bloom — WhatsApp AI Support Agent (Portfolio Demo)

Privacy Policy

Effective date: September 12, 2026

Demo / portfolio disclosure: This Privacy Policy describes a non-commercial software portfolio project. "Kettle & Bloom Coffee Roasters" is a fictional business created solely to demonstrate an AI-driven WhatsApp customer support agent. It is not a real company, does not sell real products, and does not process real orders or payments. Any resemblance to an actual business is coincidental.

1. Who Operates This Demo

This application ("the demo," "the assistant," "the agent") is a personal software portfolio project built to demonstrate an AI-assisted WhatsApp support workflow using the Meta WhatsApp Cloud API, a FastAPI backend, and the Groq LLM API. It is operated by an individual developer for demonstration and evaluation purposes, not by a registered company.

2. Information the Assistant Receives

When someone sends a WhatsApp message to the demo's connected test number, Meta's WhatsApp Cloud API delivers a webhook event to the backend. Depending on what the sender writes, the application may receive:

  • WhatsApp sender identifier — the sender's WhatsApp phone number and Meta's message ID (WAMID) for the event.
  • Message text — the plain-text content of the message the sender writes to the assistant.
  • Information the sender chooses to share in conversation — for example a name, city, business name/type, preferred coffee brew method, budget range, or estimated monthly volume, if and when the sender volunteers it while asking about products, orders, or wholesale supply.

The assistant only processes messages Meta forwards from the connected WhatsApp number. It does not scrape, purchase, or receive contact data from any other source.

3. Conversation History and Lead Information

To hold a coherent conversation, the backend keeps a short-lived, per-sender conversation state in the server's memory. This can include:

  • A bounded window of recent message history for that sender (used so the assistant can refer back to what was just said).
  • A "lead profile" of information the sender has volunteered — such as name, city, email, business name/type, brew or product preference, budget band, timeline, or estimated volume — used only to route the conversation (for example, to a human for a wholesale quote).
  • Basic conversation bookkeeping, such as turn counters, escalation status, and a record of which support tool (e.g. product lookup) was used, without payment or card data.

This state is held only in the running application's memory. It is not written to a database or disk, and is not persisted across a restart of the demo server.

4. Human Handoff Information

Some conversations (for example, a request to speak with a person, a wholesale inquiry, or a flagged issue) are routed to a "human handoff" queue for follow-up. A handoff record deliberately carries only what a human would need to help: a masked/partial version of the sender's number, the lead information described above, a short conversation summary, a bounded transcript excerpt, and the reason the conversation was escalated. In this demo the handoff queue is an in-memory, in-process list — it is not sent to any external CRM, ticketing system, or third party, and it is cleared when the demo server restarts.

5. Why This Information Is Used

  • To understand and respond to the message currently being sent.
  • To keep track of the conversation across a few back-and-forth messages.
  • To answer product and support questions using the demo's fixed product catalog and business FAQ information.
  • To recognize when a conversation should be handed to a human instead of continuing with the automated assistant.
  • To demonstrate lead-qualification behavior (e.g. distinguishing a casual question from a wholesale inquiry) as part of the portfolio project.

Information is not used for advertising, profiling, resale, or any purpose unrelated to generating and routing a reply within this demo.

6. AI-Assisted Processing

Replies are generated with the help of a large language model accessed through the Groq API. To generate a response, the relevant parts of the current conversation (the message text, a short recent history window, and static business/product information) are sent to Groq's API for processing. Deterministic checks in the application — not the model itself — decide when to escalate to a human, what counts as a supported product claim, and what the assistant is and is not allowed to say.

7. External Services Involved

Operating this demo necessarily involves two external providers:

  • Meta (WhatsApp Cloud API) — delivers incoming WhatsApp messages to the backend and delivers the assistant's replies back to WhatsApp. Meta's own privacy policy governs its handling of WhatsApp messages as the messaging platform.
  • Groq (LLM API) — receives conversation text (as described in Section 6) in order to generate the assistant's natural-language reply.

No other third party, analytics vendor, advertising network, payment processor, or data broker receives information from this demo.

8. Retention and Storage

This demo is built to keep all conversation and lead state in-memory, inside the running server process, with fixed upper bounds on how much history, lead data, and handoff records it keeps per sender. There is no external database, data warehouse, or persistent disk storage in this application. Restarting the demo server clears all conversation state, lead data, and handoff records it was holding. Message content passed to Meta and Groq is subject to those providers' own retention practices, which this project does not control.

9. Security Practices Actually Implemented

The codebase for this demo takes the following concrete steps:

  • API credentials (WhatsApp access token, Groq API key, webhook verify token) are read from local environment configuration and are never written to logs.
  • Phone numbers are masked before being written to logs (e.g. shown as ********1234), so raw numbers do not appear in application logs.
  • Exceptions from external providers are logged by error type only, not with raw provider error text, so provider responses are not incidentally logged in full.
  • Conversation and lead data are validated against a fixed schema before being stored in memory.

This is a portfolio-scale demo, not an audited production system. No formal certification (for example, a claim of "GDPR compliance," "SOC 2," or "HIPAA compliance") is made, because none has been obtained or verified for this project.

10. No Payment or Card Data

The WhatsApp assistant does not process orders, take payments, or collect card, bank, or other financial account details at any point. The fictional business data behind this demo explicitly describes payment as being handled elsewhere (a separate website checkout in the fictional scenario), never via WhatsApp. This demo does not sell anything and has no real checkout flow.

11. No Sale of Personal Information

Information received through this demo is never sold, rented, or traded to any third party. It is used only to operate the demo conversation flow described above.

12. No Unnecessary Collection

The assistant does not ask for information it does not need to answer a support question or route a lead. It does not request government ID numbers, financial account details, precise location, or any sensitive personal data category, and it is explicitly instructed not to collect payment or card details.

13. Deletion and Contact Requests

Because this is a demo with in-memory-only storage, restarting the server already clears held conversation and lead state. If you interacted with a live instance of this demo and want to confirm that no record was retained, or you have any other question about this policy, you can reach out using the contact details below.
